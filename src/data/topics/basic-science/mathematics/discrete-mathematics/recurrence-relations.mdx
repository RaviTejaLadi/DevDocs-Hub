# Recurrence Relations

**Recurrence Relations** is a technical concept you should be able to explain in plain language before relying on memorisation. A useful way to learn it is to connect the definition to a concrete example, then identify the conditions that make the example valid.

## Definition

Start with the exact meaning of the topic and the problem it solves. Separate the definition from related concepts that sound similar. This prevents a common revision error: remembering a broad description but choosing the wrong tool or rule in a practical situation.

## How It Works

Break the topic into the smallest meaningful steps. First identify the inputs or assumptions. Then apply the core rule, observe the intermediate state, and finally verify the expected output. If a step cannot be explained, return to the definition and check the missing assumption instead of memorising the result.

## Practical Application

In real projects, the interesting part is usually not the happy path. Consider validation, error handling, performance, security, or maintainability when those concerns apply to the topic. Explain why the chosen approach fits the constraints instead of presenting it as the only possible solution.

## Common Pitfalls

- Mixing the topic with a related concept that has different guarantees.
- Ignoring boundary or invalid inputs.
- Using an example without checking what it returns or changes.
- Optimising before measuring a real bottleneck.

## How to Solve

Translate the wording into the smallest mathematical or logical model. Identify the quantities given, the quantity requested, and the relationship between them. Only then choose a formula or reasoning pattern. This avoids applying a familiar formula to the wrong problem.

## Sanity Checks

Estimate the answer before calculating exactly. Check whether the final value has the correct sign, unit, range, and direction. For aptitude problems, test extreme or simple values when possible; they can reveal an invalid assumption quickly.

## Common Traps

Watch for percentage-point versus percentage changes, unit mismatches, inclusive versus exclusive counting, average versus weighted average, and hidden constraints in the wording. These mistakes often cause more wrong answers than the arithmetic itself.

## Alternative Check

When the direct method is easy to misuse, verify the result using a second viewpoint. Estimate the range first, then solve exactly. If the problem involves ratios or percentages, rewrite the quantities in a common base. If it involves counting, define what is included before applying a formula. This extra check is usually faster than correcting a wrong answer after several dependent calculations.

## Final Understanding Check

Before considering **Recurrence Relations** revised, make sure you can state the definition without relying on the example, explain the mechanism in the correct order, and predict what happens when one important input or assumption changes. Then check one boundary case and one practical use case. The example should support the explanation rather than replace it. When a result is surprising, inspect the rule that produced it and verify the relevant precondition. This approach is more reliable than memorising a code snippet, formula, command, or interview answer because the same reasoning can be applied to a new problem. For technical topics, also distinguish what is guaranteed by the language, library, protocol, or mathematical rule from what is merely a common convention. That distinction helps you choose the correct solution when the context changes.
