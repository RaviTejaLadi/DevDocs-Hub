# Union Find

**Union Find** should be learned as a sequence of decisions, not as a memorised final answer. Think of an algorithm like a recipe: the ingredients are the input, the repeated steps are the method, and the output is correct only when the rule is valid for every allowed case.

## Problem Definition

State what the algorithm receives and what it must return. Note constraints before choosing an approach because an algorithm that works for ten values may be unusable for ten million.

## Core Idea

Identify the central invariant, recurrence, ordering rule, or search condition. Then walk through one tiny example by hand. Every step should be justified by that rule rather than by pattern matching.

## Worked Example

Use a small input where every intermediate state can be written down.

// Small implementation that makes the algorithmic steps visible.
```javascript
function findMax(values) {
  if (values.length === 0) return undefined;
  let max = values[0];
  for (const value of values) {
    if (value > max) max = value;
  }
  return max;
}

console.log(findMax([4, 9, 2, 7]));
```

## Complexity and Edge Cases

Record time and space complexity separately. Then test empty input, a single value, already-ordered data, duplicates, and maximum-size constraints when those cases are meaningful.

## Common Mistakes

- Choosing an algorithm before reading the constraints.
- Explaining the result without explaining the invariant or decision rule.
- Ignoring auxiliary space used by helper structures.
- Forgetting that duplicate or boundary values may change the branch taken.

## Correctness Check

Write the invariant, recurrence, or decision rule in one sentence. During each iteration or recursive call, identify what part of the problem is already solved. At the stopping condition, connect that known state to the required output. This is a stronger explanation than memorising one input-output trace.

## Complexity

State time and auxiliary-space complexity separately. Then compare the result with the problem constraints. A simple linear solution is often preferable to a more complex technique when the input is small, while large constraints may require logarithmic, linearithmic, or specialised approaches.

## Testing Strategy

Trace one tiny example by hand, then test the smallest valid input, a boundary case, duplicates when relevant, and a larger case. When a result is wrong, inspect the intermediate state that should satisfy the invariant. This usually locates the bug faster than checking only the final output.

## Proof and Testing

A convincing algorithm explanation links the implementation to correctness. State what remains true after each major step, explain why the stopping condition is sufficient, and then give the complexity. Testing should include boundary inputs and cases that stress the part of the algorithm most likely to fail. When two approaches produce the same output, prefer the one whose correctness argument and complexity are easier to communicate under the problem constraints.

## Final Understanding Check

Before considering **Union Find** revised, make sure you can state the definition without relying on the example, explain the mechanism in the correct order, and predict what happens when one important input or assumption changes. Then check one boundary case and one practical use case. The example should support the explanation rather than replace it. When a result is surprising, inspect the rule that produced it and verify the relevant precondition. This approach is more reliable than memorising a code snippet, formula, command, or interview answer because the same reasoning can be applied to a new problem. For technical topics, also distinguish what is guaranteed by the language, library, protocol, or mathematical rule from what is merely a common convention. That distinction helps you choose the correct solution when the context changes.
