# Data Types

**Data Types** is a technical concept you should be able to explain in plain language before relying on memorisation. A useful way to learn it is to connect the definition to a concrete example, then identify the conditions that make the example valid.

## Definition

Start with the exact meaning of the topic and the problem it solves. Separate the definition from related concepts that sound similar. This prevents a common revision error: remembering a broad description but choosing the wrong tool or rule in a practical situation.

## How It Works

Break the topic into the smallest meaningful steps. First identify the inputs or assumptions. Then apply the core rule, observe the intermediate state, and finally verify the expected output. If a step cannot be explained, return to the definition and check the missing assumption instead of memorising the result.

## Example

Choose an example that is small enough to trace line by line and realistic enough to show why the concept exists.

// Small starter example for understanding the main idea.
```javascript
const input = [1, 2, 3];
const output = input.map(value => value * 2);
console.log(output);
```

## Practical Application

In real projects, the interesting part is usually not the happy path. Consider validation, error handling, performance, security, or maintainability when those concerns apply to the topic. Explain why the chosen approach fits the constraints instead of presenting it as the only possible solution.

## Common Pitfalls

- Mixing the topic with a related concept that has different guarantees.
- Ignoring boundary or invalid inputs.
- Using an example without checking what it returns or changes.
- Optimising before measuring a real bottleneck.

## Syntax vs. Behavior

Syntax shows how to write the feature; behavior explains what the runtime actually does. Learn both. Pay attention to scope, evaluation order, return values, mutation, exceptions, and asynchronous behavior when they apply. These details are where small-looking examples often become surprising.

## Practical Edge Cases

Test empty input, invalid input, duplicate values, missing properties, and error paths when the feature accepts user or external data. A short example is useful for learning syntax, but a realistic example should also show validation and a predictable result.

## Maintainable Usage

Prefer the clearest correct construct before reaching for clever shortcuts. Keep transformations small, name intermediate values when they improve readability, and avoid hidden side effects. In revision notes, the goal is not only to remember a feature but also to know when using it makes the code easier to understand.

## Practical Decision

Before using a feature, ask whether it improves correctness, readability, or performance for the specific problem. Small language features can have large semantic differences around mutation, scope, exceptions, coercion, and asynchronous execution. Prefer examples that reveal those differences rather than examples that only demonstrate syntax. When input comes from users or external systems, add validation and define the failure behavior explicitly.

## Final Understanding Check

Before considering **Data Types** revised, make sure you can state the definition without relying on the example, explain the mechanism in the correct order, and predict what happens when one important input or assumption changes. Then check one boundary case and one practical use case. The example should support the explanation rather than replace it. When a result is surprising, inspect the rule that produced it and verify the relevant precondition. This approach is more reliable than memorising a code snippet, formula, command, or interview answer because the same reasoning can be applied to a new problem. For technical topics, also distinguish what is guaranteed by the language, library, protocol, or mathematical rule from what is merely a common convention. That distinction helps you choose the correct solution when the context changes.
